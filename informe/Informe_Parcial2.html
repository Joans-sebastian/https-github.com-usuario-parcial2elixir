1. Pensamiento computacional

El pensamiento computacional se aplicó en cuatro momentos: abstraer los datos en structs y módulos que esconden los detalles,descomponer cada problema en etapas pequeñas, reconocer patrones que se repiten (dentro de cada problema y entre los dos), y la codificacion de los algoritmos recursivos de cada etapa.

1.1 Abstracción

Abstraer es quedarse con lo esencial y esconder los detalles. Las decisiones fueron:

  • Un tramo es solo %Tramo{origen, destino, minutos, costo, linea}. No importa cómo estaba escrito en el CSV; el campo linea conserva lo único que se necesita del archivo: la línea física para los reportes.
  • La red es un mapa %{centro => [tramos que salen]} (lista de adyacencia). La búsqueda solo necesita preguntar «¿qué tramos salen de aquí?».
  • Un itinerario es %Itinerario{centros, tramos, minutos, costo}: los totales se calculan una vez al construirlo.
  • El mapa es %{{fila, columna} => simbolo}. Con esta forma, una casilla fuera del borde simplemente no existe (Map.get devuelve nil) y no hacen falta if para revisar los límites.
  • Una región es %Region{id, simbolo, celdas, area, perimetro, desde, hasta}.
  • La entrada y la salida quedan detrás de Entrada y Salida: los algoritmos no saben si los datos vienen de un archivo o de una prueba, y por eso se pueden probar con datos escritos en el test.
  • Mostrar en pantalla queda detrás de Util2.mostrar/2: :mensaje o :error, sin pensar en IO.puts(:standard_error, …).

a. Diseño de los algoritmos

Itinerarios simples (DFS con backtracking) 
explorar(actual, destino, visitados, camino):
  si actual == destino → devolver [camino]
  para cada tramo que sale de actual:
    si tramo.destino no está en visitados:
      explorar(tramo.destino, destino,
               visitados + {tramo.destino},
               camino + [tramo])
  unir todos los caminos encontrados
Regiones (flood fill recursivo) 
recorrer(casillas en orden):
  si es "." o ya está asignada → seguir
  si no → explorar(casilla) y crear región id+1

explorar(casilla):
  marcar casilla como asignada
  para cada vecino (arriba, abajo, izq., der.):
    si tiene el mismo símbolo y no está asignado:
      explorar(vecino)

3.1 Validación previa recursiva: depurar la red

El patrón %Tramo{origen: c, destino: c} solo coincide si origen y destino son el mismo valor: así se detecta un bucle sin escribir un if. Un mapa vistos guarda la línea de la primera aparición de cada pareja dirigida.

lib/problema1/depuracion.ex
def depurar(tramos), do: depurar(tramos, %{}, [], [])

# Caso base: no quedan tramos. Se invierten los acumuladores.
defp depurar([], _vistos, conservados, descartes) do
  {Lista.invertir(conservados), Lista.invertir(descartes)}
end

# Bucle: el patrón exige que origen y destino sean el MISMO valor `c`.
defp depurar([%Tramo{origen: c, destino: c} = tramo | resto], vistos, conservados, descartes) do
  motivo = "bucle: el tramo sale y llega al mismo centro (#{c})"
  depurar(resto, vistos, conservados, [{tramo, motivo} | descartes])
end

# Tramo normal: se conserva solo si la pareja (origen, destino) no apareció antes.
defp depurar([tramo | resto], vistos, conservados, descartes) do
  pareja = {tramo.origen, tramo.destino}

  case Map.fetch(vistos, pareja) do
    {:ok, linea_original} ->
      motivo =
        "repetido: la pareja #{tramo.origen} → #{tramo.destino} ya se definió en la " <>
          "línea #{linea_original}; se conserva la primera aparición"

      depurar(resto, vistos, conservados, [{tramo, motivo} | descartes])

    :error ->
      depurar(resto, Map.put(vistos, pareja, tramo.linea), [tramo | conservados], descartes)
  end
end

3.2 Búsqueda recursiva de itinerarios

Como los datos en Elixir son inmutables, cada llamada recursiva recibe su propia versión de visitados; al volver de una rama, la anterior sigue intacta. Eso es el «deshacer» del backtracking, sin trabajo extra.

lib/problema1/busqueda.ex
def itinerarios(grafo, origen, destino) do
  grafo
  |> explorar(origen, destino, MapSet.new([origen]), [])
  |> Enum.map(&Itinerario.desde_tramos(origen, &1))
end

# Caso base: llegamos al destino. El camino se acumuló al revés.
defp explorar(_grafo, destino, destino, _visitados, camino_al_reves) do
  [Enum.reverse(camino_al_reves)]
end

# Caso recursivo: se prueba cada tramo de salida hacia un centro no visitado.
# Si un centro no tiene salidas, Map.get devuelve [] y la rama no aporta caminos.
defp explorar(grafo, actual, destino, visitados, camino_al_reves) do
  grafo
  |> Map.get(actual, [])
  |> Enum.reject(&MapSet.member?(visitados, &1.destino))
  |> Enum.flat_map(fn tramo ->
    explorar(
      grafo,
      tramo.destino,
      destino,
      MapSet.put(visitados, tramo.destino),
      [tramo | camino_al_reves]
    )
  end)
end

3.3 Stream infinito de centros alcanzables y por qué converge

lib/problema1/alcance.ex · hasta_estabilizar/2
def hasta_estabilizar(grafo, origen) do
  grafo
  |> secuencia(origen)
  |> Stream.with_index()
  |> Enum.reduce_while([], &comparar_con_anterior/2)
end

# Primer elemento: aún no hay con qué comparar.
defp comparar_con_anterior({estado, _paso}, []), do: {:cont, [estado]}
lib/problema1/alcance.ex · comparar_con_anterior/2
defp comparar_con_anterior({estado, paso}, [anterior | _] = estados) do
  if MapSet.equal?(estado, anterior) do
    {:halt, {Enum.reverse(estados), paso - 1}}
  else
    {:cont, [estado | estados]}
  end
end
¿Por qué converge aunque el Stream sea infinito?
  1. Stream.iterate/2 solo describe la sucesión: no calcula nada hasta que se le pide un elemento (es perezoso).
  2. Cada paso es MapSet.union(conjunto, nuevos), así que los conjuntos nunca disminuyen: S0 ⊆ S1 ⊆ S2 ⊆ …
  3. Todos son subconjuntos de los centros de la red, que son finitos (n centros).
  4. Una sucesión que solo crece y está acotada no puede crecer para siempre: después de, como mucho, n pasos un conjunto se repite. Desde ahí todos los siguientes son iguales (punto fijo), porque expandir el mismo conjunto da el mismo resultado.
  5. Enum.reduce_while/3 pide elementos uno a uno y responde {:halt, …} en la primera repetición: el consumo es finito. Para A solo se calculan 4 elementos (pasos 0 a 3).
Si el destino no está en el conjunto estable, no hay ningún camino: se informa «sin itinerarios» y se omite la búsqueda exhaustiva.

defp validar_filas([{linea, simbolos} | resto], ancho, fila, tabla, problemas) do
  columnas = Lista.contar(simbolos)

4.2 Las dos funciones recursivas que construyen las regiones

lib/problema2/regiones.ex · recorrer_casillas/5
defp recorrer_casillas([], _celdas, _asignadas, _siguiente_id, regiones) do
  Enum.reverse(regiones)
end

defp recorrer_casillas([posicion | resto], celdas, asignadas, siguiente_id, regiones) do
  simbolo = Map.fetch!(celdas, posicion)

  if simbolo == "." or MapSet.member?(asignadas, posicion) do
    # Fondo o casilla ya asignada: se salta.
    recorrer_casillas(resto, celdas, asignadas, siguiente_id, regiones)
  else
    # Casilla nueva: se explora toda su región.
    {casillas_region, asignadas} =
      explorar(posicion, simbolo, celdas, MapSet.put(asignadas, posicion), [])

    region = Region.nueva(siguiente_id, simbolo, casillas_region, celdas)
    recorrer_casillas(resto, celdas, asignadas, siguiente_id + 1, [region | regiones])
  end
end
lib/problema2/regiones.ex · explorar/5 y explorar_vecinos/5
defp explorar(posicion, simbolo, celdas, asignadas, region) do
  posicion
  |> Region.vecinos()
  |> explorar_vecinos(simbolo, celdas, asignadas, [posicion | region])
end

defp explorar_vecinos([], _simbolo, _celdas, asignadas, region), do: {region, asignadas}

defp explorar_vecinos([vecino | resto], simbolo, celdas, asignadas, region) do
  # Map.get devuelve nil fuera del mapa, así que no hace falta revisar bordes.
  if Map.get(celdas, vecino) == simbolo and not MapSet.member?(asignadas, vecino) do
    {region, asignadas} =
      explorar(vecino, simbolo, celdas, MapSet.put(asignadas, vecino), region)

    explorar_vecinos(resto, simbolo, celdas, asignadas, region)
  else
    explorar_vecinos(resto, simbolo, celdas, asignadas, region)
  end
end

Perímetro: cada casilla tiene 4 lados; un lado cuenta si del otro lado hay borde (Map.get da nil) o un símbolo distinto, incluido el fondo. Para la región C del ejemplo: 3 + 2 + 2 + 2 + 3 = 12, igual que en el enunciado.

4.3 SVG generado por fragmentos

lib/problema2/svg.ex · generar/4
def generar(ruta, mapa, regiones, paleta) do
  ancho = @tamano * mapa.columnas
  alto = @tamano * mapa.filas
  region_de = for region <- regiones, celda <- region.celdas, into: %{}, do: {celda, region}

  # Nada se calcula aquí todavía: el Stream solo describe los fragmentos.
  fragmentos =
    Stream.concat([
      encabezado(ancho, alto, paleta["."].hex),
      Stream.map(Mapa.Regiones.posiciones(mapa), &casilla(&1, mapa.celdas, paleta, region_de)),
      Stream.map(regiones, &etiqueta/1),
      ["</svg>"]
    ])

  # Al escribir se consume el Stream: cada fragmento se genera y se escribe enseguida.
  Salida.escribir(ruta, fragmentos)
end

6. Reflexión sobre el uso de inteligencia artificial

1. Herramientas usadas. Se usó ChatGPT para explicacion de algunos codigosmix test y abriendo los SVG en el navegador.

2. Interacción decisiva. Al compilar con mix compile --warnings-as-errors, el verificador de tipos de Elixir avisó «incompatible types given to Salida.escribir/2» en Mapa.Svg.generar/4. La propuesta inicial terminaba en |> Salida.escribir(ruta): con el operador pipe, el Stream del SVG quedaba como primer argumento (la ruta) y la ruta como segundo (las líneas). Se corrigió guardando el Stream en fragmentos y llamando Salida.escribir(ruta, fragmentos). Se verificó con la prueba que analiza el SVG como XML y abriéndolo en el navegador. y mi consulta preguntandole a la IA cómo estructurar correctamente el pipeline con el operador pipe (|>) para evitar cruzar los argumentos de la ruta y los datos del Stream en el módulo de salida de archivos, lo qué respondió la IA y que mr sugirió separar la llamada quitando el último pipe y pasando explícitamente los parámetros en orden de prioridad: Salida.escribir(ruta, contenido_stream). y se verifico ejecutando nuevamente mix compile --warnings-as-errors para comprobar que el linter ya no reportara incompatibilidad de tipos, y ejecutando la prueba automatizada que valida la estructura XML del SVG generado.

3. Enfoques nuevos.

(a) Detectar el bucle con el patrón %Tramo{origen: c, destino: c} en lugar de un if.

(b) Consumir un Stream infinito con Enum.reduce_while/3, que deja comparar cada estado con el anterior y detenerse con :halt.

(c) Una prueba automática que lee el código fuente de las validaciones y falla si aparece Enum. o Stream., para no romper el requisito 7 sin darme cuenta, el uso de Enum.reduce_while/3 junto con Streams infinitos fue clave para manejar la lógica de estados de manera eficiente y limpia en Elixir. Aprendí a aprovechar el control de flujo funcional mediante acumuladores y la señal :halt para cortar la ejecución de forma segura sin recurrir a bucles imperativos tradicionales.

4. Balance de aprendizaje. logro un poco comprender con claridad la estructura modular del proyecto, la definición de structs, el diseño de patrones de coincidencia (pattern matching) y la separación de responsabilidades entre el dominio, la persistencia y la interfaz de línea de comandos. y lo que puede generarme dificultad es el manejo avanzado de tipos de datos perezosos (lazy evaluation) con Streams y la depuración fina de errores de compilación estrictos bajo restricciones de inmutabilidad en concurrencia a veces requieren mayor análisis. Depronto para el proximo trabajo tendre que planificar las pruebas unitarias desde una etapa más temprana del desarrollo para detectar incompatibilidades de tipos y problemas en el flujo de datos antes de integrar los módulos principales.
